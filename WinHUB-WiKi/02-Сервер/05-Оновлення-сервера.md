# Оновлення сервера

Нову версію готуйте в окремому checkout або release-архіві. Скрипт спочатку створює backup установленого сервера, потім копіює серверні файли, додає відсутні env-параметри, встановлює dependencies, застосовує migrations і перевіряє служби.

## Із Git checkout

Git-команди виконуйте від звичайного користувача, який має доступ до репозиторію:

```bash
git -C ~/winhub pull --ff-only
sudo bash ~/winhub/WinHUB/deploy/debian/update_winhub.sh ~/winhub/WinHUB
```

Для конкретної версії спочатку виконайте `git -C ~/winhub fetch --tags`, потім `git -C ~/winhub checkout <TAG_OR_COMMIT>` і запустіть updater із підготовленого checkout. Він також приймає корінь монорепозиторію `~/winhub` та автоматично знаходить `WinHUB/`.

## Із серверного release

На машині збірки з каталогу `WinHUB/`:

```bash
bash deploy/create_release.sh
```

Передайте `dist/winhub-v<VERSION>.tar.gz` і manifest на сервер, порівняйте SHA-256 із `server_archive_sha256`, потім:

```bash
sudo bash /opt/winhub/deploy/debian/update_winhub.sh /tmp/winhub-v<VERSION>.tar.gz
```

Використовуйте release зі спільними `deploy/server-files.txt` і `server-excludes.txt`.

## Перехід зі старої структури

Якщо в `/opt/winhub` досі лежить старий Git checkout з агентами, завантажте новий checkout у `~/winhub` та запустіть **новий** updater із `~/winhub/WinHUB/deploy/debian/`, як у першому прикладі. Не виконуйте `git pull` у старому `/opt/winhub`: після зміни структури серверні файли опиняться на іншому рівні.

Updater бере backup до копіювання, зберігає `/etc/winhub`, `/var/lib/winhub` і venv. Старі сторонні каталоги в `/opt/winhub` автоматично не видаляються: після успішної перевірки їх можна перенести в локальний архів. Нові інсталяції відразу містять лише сервер.

Updater без аргументів із установленого `/opt/winhub` повідомляє, що потрібно передати джерело оновлення. Git ref тепер вибирається в окремому checkout.

Наявний `HISTORY_SEARCH_KEY` зберігається. Якщо його раніше не було, updater додає порожнє значення: сервер продовжує використовувати попередній task HMAC fallback, зберігаючи сумісність індексу. Окремий ключ автоматично створюється лише на новій інсталяції; його зміна на чинному сервері потребує переіндексації історії.

## Перевірка

```bash
sudo /opt/winhub/deploy/debian/healthcheck_winhub.sh
sudo systemctl status winhub --no-pager
sudo journalctl -u winhub -n 100 --no-pager
```

Не замінюйте `winhub.env` шаблоном і не використовуйте installer для звичайних оновлень. Перенесіть backup у off-host storage. Rollout агентів виконуйте після перевірки сервера.
