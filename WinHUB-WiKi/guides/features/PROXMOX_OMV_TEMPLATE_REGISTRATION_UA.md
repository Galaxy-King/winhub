# Масове підключення OMV і реєстрація шаблону 9006

Інструмент: [register_omv_template.py](../../../WinHUB/deploy/proxmox/register_omv_template.py).
Запускається через Python 3 у WSL, без сторонніх Python-пакетів; на вузлах потрібні root SSH,
Python 3, Proxmox pvesm/pvesh/qm та findmnt. Агент WinHUB для цього сценарію не потрібен.

## Підготовка у WSL

```bash
mkdir -p ~/PVE_Script/winhub-deploy
cp /mnt/c/Users/spock/OpenCloud/Personal/WinHUB_Project/WinHUB/deploy/proxmox/register_omv_template.py ~/PVE_Script/winhub-deploy/
cd ~/PVE_Script/winhub-deploy
python3 ./register_omv_template.py --hosts ../1C_Project.txt
```

За потреби додайте `--identity ~/.ssh/id_ed25519` та `--port 22`.
Список містить IPv4 або root@IPv4, по одному на рядок. Порожні рядки, коментарі після #,
UTF-8 BOM/CRLF та дублікати підтримуються. root@IP та IP вважаються одним destination.
Починайте з тестового списку на один сервер.

## Інтерактивні параметри

| Запит | Типове значення |
| --- | --- |
| OMV server IPv4 | 10.97.197.100 |
| SMB share name | Proxmox |
| SMB username | proxmox |
| SMB domain | Порожньо |
| SMB password | Вводиться приховано, без типового значення |

Для ресурсу `//10.97.197.100/Proxmox` IP і share вводяться окремо.
ID сховища OMV і template VMID 9006 визначені константами на початку скрипта;
готова конфігурація прив’язана до наявних трьох дисків саме шаблону 9006.
Перед підтвердженням відображаються IP/share та кількість вузлів, пароль не відображається.

## Поведінка

1. Перевіряє, що це Proxmox і SSH працює від root.
2. Перевіряє конфлікт VMID 9006 у всьому кластері до змін storage.
3. Для наявного OMV порівнює CIFS type, точний server IPv4, share, username, domain та відсутність subdir.
   При відмінності відмовляється змінювати сховище. Наявні credentials зберігаються.
4. Якщо OMV немає, додає його через `pvesm add cifs` з усіма показаними у GUI типами контенту:
   Disk image, ISO, Container template, Backup, Container, Snippets, Import.
   SMB-версія узгоджується штатно Proxmox, SMB1 не вмикається.
5. Для відповідного наявного storage додає Images, якщо його немає, зберігаючи решту content.
   Якщо nodes обмежені, додає поточний вузол до списку, зберігаючи попередні.
   Вимкнений storage автоматично не вмикає.
6. Перевіряє active та реальне CIFS-монтування саме з введеного IP/share.
7. Перевіряє vmbr1, наявність і ненульовий розмір system/EFI/Cloud-Init дисків через pvesm path.
8. Створює `/etc/pve/qemu-server/9006.conf` exclusive, без перезаписування.
   Якщо на цьому вузлі вже є відповідний template, повторний запуск нічого не переписує.
9. Читає конфіг через qm для контролю. Переходить до наступного хоста навіть після помилки.

Сховище відображається у Proxmox GUI. Прямих записів credentials/storage у storage.cfg немає:
це робить штатний CIFS plugin Proxmox. Пароль передається через зашифрований SSH stdin,
не потрапляє у локальні аргументи SSH, history чи результати. На вузлі pvesm отримує пароль через
локальний argv, тому root може короткочасно бачити його; Proxmox зберігає його у privileged storage credentials.

## Межі операції

Це реєстрація вже наявного спільного template: скрипт не копіює образи, не запускає ВМ,
не виконує qm template і не змінює спільні диски. machine pc-q35-11.0+pve2 та CPU із заданої
конфігурації мають підтримуватися цільовим вузлом; сумісність фактичного запуску перевіряється тестовим клоном.
Після реєстрації для WinHUB задавайте Source template VMID=9006, Target storage=local.

На незалежних Proxmox кожний отримує власний конфіг для тих самих base-дисків.
У кластері конфіг синхронізується через pmxcfs: якщо VMID вже зареєстровано на іншому вузлі,
скрипт відмовляється створювати дублікат. Міграція/переприв’язка шаблону — окреме адміністрування.
Не запускайте паралельне створення VMID 9006 іншими інструментами під час реєстрації.

Якщо сховище додано, а подальша перевірка не пройшла, storage залишається для діагностики,
template не реєструється. Скрипт не видаляє конфіг або диски при помилці. При timeout/перериванні
перевірте результат на поточному хості перед повтором. Спільний шаблон не запускають і не видаляють
з незалежних вузлів; супровід base-дисків виконується централізовано.

Локальні тести використовують тимчасові файли та mocks. Живий rollout на Proxmox автором скрипта
не виконувався. Результат success означає перевірене монтування й реєстрацію конфігурації,
а не виконаний запуск Windows чи тест backup.

Сумісність EFI: нові реєстрації не додають ms-cert=2023k, який відсутній у схемі старих Proxmox. Якщо qm config пропускає efidisk0, скрипт перевіряє вихідний конфіг, зберігає backup у /var/lib/winhub-proxmox-admin/config-backups і прибирає лише цей параметр із відомого template. Locked/snapshot конфіг не виправляється автоматично. Диски та EFI-ключі всередині диска не переписуються. Інші параметри, зокрема machine version, теж мають підтримуватися вузлом; успіх реєстрації не підтверджує запуск клона.
