# Створення Windows Server 2025 VM

| Параметр | Значення |
| --- | --- |
| Віртуалізація | Proxmox VE |
| Операційна система | Windows Server 2025 Standard (Desktop Experience) |
| Golden Template | **9006 — TPL-WS2025-CLOUDINIT** |
| Сховище шаблону | **OMV** |
| Сховище нових ВМ | **local** |
| Тип клонування | **Full Clone** |
| Автоматизація | WinHUB |
| Первинне налаштування ОС | Cloudbase-Init / ConfigDrive |
| Моніторинг | Zabbix Agent 2 |

Шаблон містить Windows, базові оновлення, драйвери VirtIO, QEMU Guest Agent і Cloudbase-Init та підготовлений через Sysprep. Робочі користувачі, VPN, прикладне ПЗ, WinHUB Agent для Windows та RDS налаштовуються після створення.

Шаблон **9006** замінює попередній **9005** для цього сценарію. Golden Template не запускають і не змінюють під час звичайного створення ВМ. Оновлення образу виконує відповідальний адміністратор централізовано.

## 1. Основний сценарій — створення через WinHUB

### 1.1. Передумови

- На цільовому Proxmox доступний і схвалений Linux Agent WinHUB.
- Агенту дозволена дія `run_script`, а оператору — запуск затвердженого шаблону на цьому хості.
- Шаблон `9006` зареєстрований на цільовому Proxmox, його диски на `OMV` доступні.
- На `local` увімкнені типи вмісту **Disk image** та **Snippets**, достатньо вільного місця.
- Виділена вільна IP-адреса, відомі маска, шлюз та DNS. Відсутність відповіді на ping не доводить, що IP вільний.
- У WinHUB імпортований і затверджений актуальний шаблон **Proxmox — Create Windows VM**.

У кластері VMID має бути вільний у всьому кластері. На незалежних Proxmox конфігурація шаблону не з’являється автоматично лише через підключення `OMV`; її реєстрацію виконує адміністратор. Заборонено одночасно змінювати чи видаляти спільні base-диски з різних серверів.

### 1.2. Заповнення задачі

Виберіть **один Proxmox-хост**, на якому потрібно створити ВМ. Не запускайте створення на групі хостів.

| Поле | Як заповнювати |
| --- | --- |
| Source template VMID | **9006**; перевіряйте значення, навіть якщо форма пропонує інше |
| Proxmox VM name | Назва для Proxmox, наприклад `term-192.168.38.236` |
| Windows hostname | Необов’язково. Порожньо — випадкове `WIN-XXXXXXXXXX`; власне ім’я — до 15 символів, літери/цифри/дефіси, починається з літери |
| New VM ID | Порожньо — перший вільний номер від **100**, з урахуванням ВМ, контейнерів і шаблонів кластера |
| Operation | Спочатку **Validate**, потім **Create** |
| Target storage | **local** |
| IPv4 address | Виділена статична IP-адреса |
| Subnet mask or prefix | Наприклад `24` або `255.255.255.0` |
| Default gateway | Шлюз цієї підмережі |
| DNS servers | IPv4 DNS через пробіл; для AD — корпоративні DNS домену |
| Network bridge / VLAN ID | Порожньо — успадкувати із шаблону; за потреби вказати явно |
| CPU cores / Memory in MiB | Порожньо — успадкувати; RAM задається у MiB |
| System disk size in GiB | Порожньо — успадкувати; допускається лише збільшення |

Вихідний шаблон має 8 ядер, 16 384 MiB RAM та диск 110 GiB; фактичні значення перевіряйте у поточному образі. Збільшення віртуального диска не означає автоматичного розширення розділу Windows.

Для повного клонування задайте timeout задачі щонайменше **30 хвилин**; повільне сховище може потребувати більше часу.

### 1.3. Перевірка і створення

1. Запустіть **Validate**. Цей режим перевіряє параметри, шаблон і конфігурацію сховища, але не створює ВМ і не резервує VMID.
2. Після успішної перевірки змініть **Operation → Create** та запустіть задачу з тими самими параметрами.
3. WinHUB повторно перевірить параметри, виконає Full Clone на `local`, передасть мережу, Windows hostname і випадковий пароль через ConfigDrive, потім запустить ВМ.
4. Збережіть із результату **vmid**, **windows_hostname**, **username** та **temporary_password**. У Create номер і випадкове ім’я можуть відрізнятися від попереднього Validate.
5. Дочекайтеся першого запуску Windows. Орієнтир — 2–5 хвилин; можливі перезавантаження. Стан дивіться через Proxmox Console.

`VM started` означає запуск ВМ, а не підтвердження готовності ОС, застосування пароля чи доступності RDP.

Якщо задача завершилася помилкою або timeout, спочатку перевірте VMID і Proxmox task log. Частково створена ВМ автоматично не видаляється. Не запускайте повторне Create навмання і не створюйте дві ВМ з однаковою IP.

### 1.4. Перший вхід і контроль

Підключіться через RDP до заданої IP:

```text
User: .\Administrator
Password: temporary_password з результату Create
```

За потреби виберіть «Інший обліковий запис», щоб не використовувалися збережені credentials.

Перевірте у Windows:

```powershell
hostname
ipconfig /all
Get-Service cloudbase-init
```

Після завершення роботи Cloudbase-Init стан його служби `Stopped` може бути нормальним. Якщо параметри не застосувалися, перевірте журнал:

```powershell
Get-Content 'C:\Program Files\Cloudbase Solutions\Cloudbase-Init\log\cloudbase-init.log' -Tail 150
```

Змініть тимчасовий пароль Administrator і збережіть актуальний у KeePass. Тимчасовий пароль міститься в результаті задачі та ConfigDrive metadata; у Wiki його не копіюють. Перевірте повторний RDP-вхід після перезавантаження.

### 1.5. Введення в експлуатацію

Подальші дії однакові для автоматичного й ручного створення:

1. **VPN.** За відсутності конфігурації створіть заявку Jira: Project **Network Engineering (NET)**, Issue Type **VPN Server Deployment**, відповідна локація термінала; отримувач конфігів — `terminals@syneforge.com`. Установіть WireGuard і персональний конфіг.
2. **Windows Agent WinHUB.** Перевірте системний час. Установіть актуальний затверджений агент за його інструкцією, з правильними HTTPS-адресою, TLS pin та enrollment credentials. Перевірте службу, появу хоста, Approval і доступність у WinHUB. Linux Agent на Proxmox не замінює Windows Agent у ВМ.
3. **ПЗ.** Через затверджені сценарії WinHUB установіть потрібні версії Zabbix Agent 2, VeraCrypt, браузерів, Office/Acrobat, Java, 1C/BAF, Медок та іншого ПЗ відповідно до задачі. Універсальний базовий образ не повинен містити все прикладне ПЗ.
4. **RDS.** Для користувацького термінала налаштуйте потрібні ролі, політики та ліцензування за корпоративною RDS-інструкцією. Звичайний адміністративний RDP не замінює RDS Session Host і CAL. Перевірте RD Licensing Diagnoser.
5. **Оновлення та час.** Налаштуйте WSUS і корпоративні NTP-сервери, установіть оновлення. Повідомте відповідального адміністратора для перевірки реєстрації у WSUS.
6. **Моніторинг.** Налаштуйте адресу Zabbix Server, унікальний Hostname, TLS-PSK та групу моніторингу. Перевірте службу й фактичне надходження даних у Zabbix.
7. **Захист і backup.** Виконайте шифрування за затвердженою процедурою зі збереженням recovery-даних, додайте ВМ у backup-політику та перевірте результат резервування.
8. **Локалізація та облік.** Налаштуйте потрібні мову, регіональні формати й розширення браузерів. Заповніть [Terminals INFO](https://wiki.syneforge.com/display/ITSUP/Terminals+INFO), збережіть актуальні credentials у KeePass.

Перед передачею перевірте мережу, VPN, RDP, WinHUB, WSUS/NTP, Zabbix, потрібне ПЗ, RDS, шифрування, backup та документацію.

## 2. Резервний сценарій — створення вручну через Proxmox

Використовуйте, якщо WinHUB недоступний або автоматична задача не може бути виконана. Передумови щодо IP, сховищ, доступності шаблону й ліцензування залишаються чинними.

### 2.1. Перевірка шаблону

У Proxmox або SSH перевірте:

```bash
pvesm status
qm config 9006
```

Очікується `template: 1`, системний та EFI-диски на `OMV`, `citype: configdrive2`, Cloud-Init-диск `ide2`, `agent: 1`. Наявність `agent: 1` сама по собі не доводить, що QEMU Guest Agent працює в гостьовій ОС.

### 2.2. Full Clone

1. Виберіть **9006 — TPL-WS2025-CLOUDINIT → Clone**.
2. Задайте вільний у кластері VMID.
3. Для цього простого резервного сценарію задайте коротке ім’я без крапок, до 15 символів, наприклад **term-38-236**. Воно використовуватиметься і для Proxmox, і для Windows.
4. Виберіть **Full Clone** та цільове сховище **local**.
5. Дочекайтеся успішного завершення. **ВМ поки не запускайте.**

Linked Clone для цього сценарію не використовується. Довга назва Proxmox із окремим Windows hostname підтримується основним сценарієм WinHUB; не перейменовуйте ручний клон після генерації ConfigDrive без перевірки metadata.

### 2.3. Параметри до першого запуску

У розділі **Hardware** задайте потрібні CPU, RAM, міст/VLAN та, за потреби, збільшіть диск. Переконайтеся, що диски нової ВМ розташовані на `local`.

У **Cloud-Init** задайте:

| Параметр | Значення |
| --- | --- |
| User | `Administrator` |
| Password | Унікальний тимчасовий пароль із менеджера паролів; великі/малі літери, цифри, спеціальні символи |
| DNS servers | Потрібні DNS |
| IP Config (net0) | Статична IP з префіксом та шлюз |
| Upgrade packages | `No` |

Натисніть **Regenerate Image**. Не копіюйте пароль із `qm config`: він може повертати `**********` замість справжнього значення. Не підключайте metadata snippet від іншої ВМ.

Перевірте конфігурацію нового клона, замінивши `<VMID>` його номером:

```bash
qm config <VMID>
```

Перевірте власні диски, MAC, UUID та VM generation ID; не копіюйте ці ідентифікатори вручну з іншої ВМ. У клона з чистого шаблону не повинно бути чужого `cicustom`.

### 2.4. Запуск і завершення

1. Запустіть нову ВМ та відкрийте **Console → noVNC**.
2. Дочекайтеся завершення Sysprep/Cloudbase-Init і можливих перезавантажень. Підготовлений образ має пройти перший запуск без ручного введення мережі.
3. Якщо з’явилися неочікувані екрани OOBE, не обходьте їх зміною випадкових параметрів: перевірте правильність шаблону з відповідальним адміністратором.
4. Увійдіть через RDP як `.\Administrator` з паролем, заданим у Cloud-Init.
5. Виконайте контроль із пункту **1.4** та введення в експлуатацію з пункту **1.5**.

У разі помилки пароля перевірте консоль і журнал Cloudbase-Init. Відновлення через QEMU Guest Agent виконує адміністратор після перевірки конкретної ВМ; це не заміна виправлення образу чи ConfigDrive.
