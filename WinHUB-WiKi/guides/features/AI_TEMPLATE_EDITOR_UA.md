# AI-редактор шаблонів

AI-редактор створює PowerShell/Bash-скрипт, окремий Jinja-звіт або пару «скрипт + звіт» через уже налаштований Open WebUI. Модель отримує версійний контракт WinHUB: формат результатів агента, контекст звіту та дозволені конструкції Jinja. Це генератор приватних чернеток, а не автономний адміністратор хостів.

## Як користуватися

1. В Infrastructure відкрийте створення/редагування шаблону, потім його редактор коду й кнопку **AI-редактор**. У редакторі JSON-схеми змінних кнопка прихована.
2. Виберіть PowerShell або Bash. Для шаблону типу report використовується Jinja. За потреби залиште **Також створити шаблон звіту**.
3. Напишіть промпт. Наприклад: «Збери WireGuard endpoints без private/preshared keys. Поверни JSON. Створи коротку таблицю Host / endpoint:port; якщо WireGuard відсутній — познач це, не встановлюй ПЗ».
4. **Додати поточний код як контекст** — необов'язкова галочка, початково вимкнена. Без неї текст відкритого скрипта не надсилається моделі. Перевірте й видаліть секрети самостійно: автоматичне маскування не гарантує виявлення всіх значень.
5. Натисніть **Створити чернетку**. Можна закрити вікно й пізніше знайти результат у власній історії. Закриття вікна не скасовує серверний запит; для цього є **Скасувати запит**. Скасування відкидає пізню відповідь, але не гарантує переривання обчислення на стороні Open WebUI.
6. Перегляньте **Код**, **Шаблон звіту**, **Зміни** та діагностику. Перевірка запускає тільки парсери й тестовий Jinja-render, не сам PowerShell/Bash-скрипт.
7. **Застосувати код у редакторі** змінює тільки текст відкритого редактора. **Зберегти нові шаблони** створює окремі непогоджені шаблони в категорії `AI drafts`, включно з пов'язаним звітом. Повторне збереження тієї ж чернетки повертає ті самі ID.
8. Перегляньте зміни й окремо затвердьте шаблони через штатний процес. Для пари спочатку затвердіть звіт, потім скрипт. Перший запуск виконуйте явно на тестовому хості відповідної ОС.

Після ручних змін можна знову відкрити AI-вікно й натиснути **Перевірити код редактора без ШІ**. Це нова приватна спроба перевірки поточного тексту без звернення до моделі; попередня перевірка не підтверджує змінений код. Синтетичний результат і пов'язаний звіт беруться з вибраної чернетки, якщо вона є. Якщо ви змінили структуру JSON-виводу, згенеруйте узгоджений звіт і fixture заново. **Перевірити ще раз** перевіряє саме збережену AI-чернетку, а не поточний текст основного редактора.

У першій версії немає автоматичного виправлення з нескінченними спробами, виконання коду для «тестування», доступу моделі до БД/хостів, RAG по всій інфраструктурі або команд на кшталт «перезавантаж сервер». Помилку можна виправити новим промптом або вручну.

## Права

- Потрібні **обидва** права Infrastructure: `manage_templates` і `use_ai_templates`. Superadmin має доступ за штатною політикою.
- `use_ai_templates` надається явно; загальний доступ до модуля не вмикає AI-редактор автоматично.
- API-key sessions не можуть використовувати редактор. Ключ Open WebUI зберігається лише на сервері WinHUB і не повертається браузеру.
- Історія чернеток приватна для автора, зокрема інший адміністратор не отримує її через AI API.
- Навіть автор/адміністратор не запускає непогоджений AI-template через звичайну кнопку задачі. Потрібне окреме затвердження з чинним content hash. Затвердження не запускає задачу.

## Open WebUI

Використовується спільне налаштування **AI / Open WebUI**, описане в [AI-звітах](../../08-Експлуатація/01-AI-звіти-Open-WebUI.md). Окремого API key у вікні редактора немає.

Для описаної інсталяції:

| Поле | Значення |
| --- | --- |
| Open WebUI URL | `http://10.13.13.6:3000` — без `/api` у кінці |
| Model ID | `Qwen3-Coder-30B-A3B-Instruct-Q5_K_M.gguf`, **якщо цей ID досі повертає ваш `/api/models`** |
| Service account API key | Ключ окремого користувача інтеграції, не адміністратора |

Модель має повертати JSON за інструкцією; сумісність протоколу не означає гарантовану якість кожного скрипта. Фактичний запит до цієї приватної інсталяції під час розробки не виконувався.

Для HTTP у захищеній мережі потрібні `AI_ALLOW_INSECURE_HTTP=true` і `10.13.13.6` у наявному `OUTBOUND_ALLOWED_HOSTS`. Не перезаписуйте інші дозволені інтеграції. HTTP не шифрує API key і промпт у дорозі; рекомендоване довготривале налаштування — HTTPS із довіреним сертифікатом.

Важливо налаштувати **сам Open WebUI**: integration account без terminal, code interpreter, Tools/Functions, MCP та доступу до сторонніх баз/секретів; модель без підключених виконуваних extensions. WinHUB надсилає `tools: []`, порожній `tool_ids`, вимкнені додаткові features, не прикріплює terminal/chat/session і відхиляє `tool_calls`. Однак сторонні server-side filters/functions і конфігурація сервера залишаються відповідальністю адміністратора. Значення цих параметрів та права описані в [офіційному API Open WebUI](https://docs.openwebui.com/reference/server-side-tool-calling/).

## Ізольована перевірка на Debian

Штатні install/update встановлюють:

- користувача `winhub-validator`, окремого від web/gateway/renderer;
- `winhub-code-validator.socket` → `/run/winhub-code-validator.sock`;
- короткоживучий `winhub-code-validator@.service`, один процес на з'єднання;
- root-owned worker і фіксований PowerShell wrapper; без права змінювати їх із web process.

Служба не читає `/etc/winhub`, `/var/lib/winhub`, `/var/log/winhub` або домашні каталоги; не імпортує Flask/БД; має private temp, read-only filesystem і заборонену мережу. Межі: 35 секунд на службу, 15 секунд на окремий parser, RAM 768 MiB, 64 tasks, до 4 з'єднань. PowerShell JIT не сумісний із `MemoryDenyWriteExecute`, тому ця опція навмисно не додається. Відсутність валідатора **не** запускає код або локальний fallback у Flask: Apply/Save блокуються.

Нові env-параметри (стандартний update додає відсутні, зберігаючи поточні):

```ini
CODE_VALIDATOR_SOCKET=/run/winhub-code-validator.sock
AI_MAX_HTTP_RESPONSE_BYTES=4194304
```

`CODE_VALIDATOR_SOCKET` має збігатися з `ListenStream` unit-файла; для звичайної інсталяції не змінюйте його. HTTP cap обмежує декомпресовану відповідь до JSON parsing, окремо від ліміту власне коду/звіту.

### PowerShell parser

На Debian потрібний `pwsh` (PowerShell 7). Встановіть його з довіреного Microsoft package source за [офіційною інструкцією для вашої версії Debian](https://learn.microsoft.com/en-us/powershell/scripting/install/install-debian). WinHUB не завантажує і не встановлює парсер за відповіддю моделі.

Перевірка після встановлення:

```bash
command -v pwsh
pwsh -NoLogo -NoProfile -NonInteractive -Command '$PSVersionTable.PSVersion.ToString()'
sudo systemctl is-active winhub-code-validator.socket
sudo bash /opt/winhub/deploy/debian/healthcheck_winhub.sh
```

Додатково можна встановити ShellCheck із Debian repository та перевірений адміністратором PSScriptAnalyzer. Без них є попередження, але базовий parser продовжує працювати:

```bash
sudo apt-get install shellcheck
sudo pwsh -NoLogo -NoProfile -Command 'Install-Module -Name PSScriptAnalyzer -Scope AllUsers'
```

Перевірте publisher/source та оберіть схвалену версію відповідно до своєї політики; для відтворюваної інсталяції використовуйте `-RequiredVersion`. Модуль має бути в root-owned глобальному каталозі `/usr/local/share/powershell/Modules`, не у домашньому каталозі адміністратора. Worker завантажує лише цей довірений модуль із фіксованим переліком built-in rules; не приймає custom rules/settings від ШІ. [Документація PSScriptAnalyzer](https://learn.microsoft.com/en-us/powershell/utility-modules/psscriptanalyzer/overview).

PowerShell 7 перевіряє синтаксис, але **не підтверджує повну сумісність із Windows PowerShell 5.1**, доступність Windows cmdlets чи права на хості. Bash-парсер на Debian так само не підтверджує наявність GNU-команд на macOS. Це зазначено в діагностиці/контракті; реальна перевірка поведінки — окремий явно запущений canary на відповідній ОС.

### Діагностика

```bash
sudo systemctl status winhub-code-validator.socket --no-pager
sudo journalctl -u 'winhub-code-validator@*' -n 80 --no-pager
id winhub-validator
sudo stat -c '%U:%G %a %n' /run/winhub-code-validator.sock /opt/winhub/core/code_validator.py
```

- **Кнопки Apply/Save неактивні:** подивіться діагностику; потрібен успішний validator і незмінений hash коду. Недоступний `pwsh` — не помилка API key.
- **Queued не змінюється:** перевірте, що WinHUB запустив `process_ai_templates_job`, PostgreSQL доступний і scheduler увімкнений у вашій топології.
- **AI draft failed:** перевірте ввімкненого provider, точний Model ID, доступ автора; модель могла повернути невалідний JSON або порушити контракт. Сирий output не додається в повідомлення помилки/логи.
- **Report fixture:** звірте поля `results[*].host`, `results[*].data` і `summary`. Не використовуйте недоступні Jinja filters/calls. Fixture — синтетичний приклад, не дані ваших серверів.
- **Legacy substitution:** AI-скрипти v1 використовують конфігураційні константи. `{{variable}}`/`{{secret:...}}` у виконуваному AI-коді відхиляються навіть після ручного редагування. Це обмеження не стосується Jinja-звітів.

Ліміти: промпт 4000 символів; reference code 64 KiB; bundle 128 KiB; companion report 32 KiB; synthetic sample 16 KiB; до 2 queued/running генерацій автора; до 3 нових генерацій/перевірок за хвилину; глобальний admission cap 50 queued/running. Останній cap є best-effort між одночасними авторами, не замінює systemd resource limits. Повторна перевірка чернетки — не частіше ніж раз на 10 секунд. Історія прибирається scheduler через 30 днів; уже збережені шаблони залишаються.
