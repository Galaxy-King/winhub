# Newsletter: посібник користувача й адміністратора

Newsletter створює поштові розсилки, перевіряє аудиторію до запуску та виконує доставку через окремий стійкий worker. Кампанія і стан кожного отримувача зберігаються в БД, тому сторінку можна закрити без втрати прогресу.

## Права

| Дозвіл | Можливості |
| --- | --- |
| `view_newsletter` / legacy `View` | Відкрити модуль і переглядати власні кампанії |
| `send_campaigns` | Створювати, скасовувати та повторювати власні кампанії |
| `manage_lists` | Створювати, перейменовувати й видаляти списки |
| `manage_smtp` | Керувати mail, inbound і LDAP-профілями |
| Administrator | Перегляд усіх кампаній і повне керування |

Право перегляду саме по собі більше не запускає розсилку.

## Індикатори готовності

У верхній частині сторінки показано кількість поштових профілів, кількість доступних списків і heartbeat служби `winhub-newsletter`. Якщо worker не активний, нову кампанію можна поставити в чергу, але доставка не почнеться до відновлення служби.

## Налаштування mail profile

1. Відкрийте **Налаштування → Mail Profiles**.
2. Вкажіть email, SMTP host, port і пароль/app password.
3. Для inbound додайте IMAP host, port, user, password і folders.
4. За потреби вкажіть GPG keyserver. Автоматичний імпорт ключів за замовчуванням вимкнений: ключ спочатку має перевірити адміністратор.
5. Натисніть **Test Mail Profile**. Перевірка виконує SMTP login, надсилає контрольний лист на адресу самого профілю і окремо перевіряє IMAP.
6. Збережіть профіль лише після успішної перевірки.

Під час перейменування профілю Newsletter оновлює посилання inbound routes. Видалення профілю, який використовується маршрутом, блокується.

## Списки отримувачів

Ім’я списку може містити латинські літери, цифри, `.`, `_` і `-`, максимум 80 символів. Один список може містити до 10 000 записів.

Отримувачів можна вставляти через кому, пробіл або новий рядок. Повні адреси перевіряються під час збереження. Для короткого імені без `@` застосовується домен, показаний над вибором аудиторії. Перед production-використанням обов’язково задайте власний `NEWSLETTER_RECIPIENT_DOMAIN`.

Перейменування є однією серверною операцією і оновлює inbound routes. Видалення списку, який використовується маршрутом, блокується.

## Створення кампанії

Форма має чотири кроки:

1. **Відправник** — виберіть mail profile.
2. **Аудиторія** — виберіть один або кілька списків.
3. **Повідомлення** — заповніть тему, текст і вкладення.
4. **Перевірка і запуск** — натисніть **Перевірити розсилку**.

Preflight об’єднує й дедуплікує адреси, відхиляє невідомі списки та некоректні адреси, показує точну кількість унікальних отримувачів і при ввімкненому GPG перевіряє ключ кожного отримувача. Після будь-якої зміни форми або вкладень preflight потрібно повторити.

Після успішної перевірки ще раз звірте резюме й підтвердьте постановку в чергу. Якщо API або мережа повернули помилку, форма й локальна чернетка не очищаються.

## GPG

GPG увімкнено за замовчуванням. Тіло і вкладення шифруються окремо для кожного отримувача; тема, адреса відправника й адреса отримувача залишаються поштовими метаданими.

У production `NEWSLETTER_ALLOW_KEYSERVER_AUTO_IMPORT=false`. Відсутній ключ потрібно імпортувати через адміністративний GPG workflow після перевірки fingerprint. Не вмикайте автоматичний імпорт без окремого затвердженого процесу перевірки ключів.

## Статуси кампанії

| Статус | Значення |
| --- | --- |
| `Queued` | очікує worker |
| `Sending` | виконується доставка |
| `Completed` | усі адреси успішні |
| `Partial` | частина доставок неуспішна або невизначена |
| `Failed` | немає успішних доставок або сталася критична помилка |
| `Cancelled` | невиконані доставки скасовано |

Кнопка **Скасувати** зупиняє лише адреси, які ще не почали оброблятися. **Повторити невдалі** повертає в чергу лише `Failed` і `Skipped`. Стан `Unknown` не повторюється автоматично, оскільки worker міг встигнути передати лист SMTP до аварії; автоматичний retry міг би створити дублікат.

## Inbound Relay

Inbound route читає один mail profile і відправляє розшифрований лист на списки та LDAP-групи, явно закріплені за цим route. Префікси `[list:...]` або `[ldap:...]` у темі не використовуються.

Для активного route обов’язкові IMAPS mail profile, точний allowlist адрес `From`, один або більше перевірених GPG signer fingerprints, цільовий список/LDAP-група, outbound profile і приватний ключ mailbox.

Лист приймається лише тоді, коли він одночасно:

1. надійшов від дозволеної адреси;
2. зашифрований на ключ WinHUB;
3. має валідний GPG-підпис із дозволеним fingerprint;
4. має новий `Message-ID`.

Після приймання створюється durable кампанія. IMAP-лист переміщується у `Processed`; повторний `Message-ID` відхиляється. Некоректні листи переміщуються у `Failed`.

Legacy env mailbox потребує `NEWSLETTER_INBOUND_ALLOWED_FINGERPRINTS`. Без нього inbound fail-closed і не запускає розсилки.

## LDAP / FreeIPA

LDAP profile можна перевірити до збереження. Для production використовуйте read-only service account, TLS і явний allowlist груп. Inbound route із LDAP-групами повинен посилатися на конкретний LDAP profile.

## Діагностика

```bash
sudo systemctl status winhub-newsletter --no-pager
sudo journalctl -u winhub-newsletter -n 100 --no-pager
sudo systemctl restart winhub-newsletter
```

Перевіряйте також картку кампанії, Audit Log, папку `Failed`, mail profile test і outbound allowlist. Не передавайте в діагностиці паролі, приватні ключі, повні списки адрес або розшифрований вміст листів.
