# Сповіщення WinHUB

## Дзвіночок і історія

Дзвіночок доступний в авторизованому повному та мобільному інтерфейсі. Червоний лічильник показує непрочитані сповіщення. На комп'ютері відкривається бічна панель, на телефоні — повноекранна шторка. Нові події у відкритому застосунку можуть показувати короткі спливні картки з переходом до деталей.

- `All notifications`, `Unread`, `Requires review` та фільтри за категорією допомагають знайти події.
- `Open details` відкриває конкретну подію; після входу можна переглянути актуальний стан і перейти до відповідного розділу.
- `Mark all read` синхронізує прочитання між пристроями користувача.
- `Clear read`, `Clear all` та `Clear` прибирають лише вашу історію сповіщень. Задачі, журнал аудиту й заявки на погодження залишаються.
- У списку доступні останні 500 дозволених сповіщень за 90 днів. Старі записи автоматично прибираються. Історичні події до встановлення оновлення не імпортуються.
- Зелений — успіх; червоний — помилка; жовтий — попередження / потрібна перевірка; блакитний — інформація. Погоджені іншим адміністратором заявки отримують позначку `Resolved` і зникають із фільтра `Requires review`.

## Події та одержувачі

| Подія | Одержувач |
| --- | --- |
| Новий хост очікує погодження; конфлікт ідентичності | Активні суперадміністратори |
| Шаблон або рецепт Software очікує погодження | Активні суперадміністратори |
| Шаблон / рецепт погоджено | Автор, якщо доступ збережено |
| Інсталятор підготовлений або підготовка не вдалася | Автор завантаження з правом керування Software |
| Завершення ручної задачі на одному чи кількох хостах | Ініціатор із доступом до Queue та всіх цілей |
| Результат розгортання Software | Ініціатор із доступом до Software і цілей |
| Завершення запуску Scheduler, у тому числі delivery / execution failure | Власник запуску з доступом до Scheduler і цілей |
| Звіт готовий; результат AI-звіту або доставки звіту | Ініціатор із доступом до Reports і цілей |
| Завершення rollout агентів | Автор із доступом до керування хостами |
| Завершення розсилки | Автор із доступом до Newsletter |
| Подія `System` зі статусом `Error` / `Critical` у системному аудиті | Активні суперадміністратори |

Групова задача формує одне підсумкове повідомлення, наприклад `18/20 successful`. Software не дублює його окремими повідомленнями про кожну внутрішню задачу. Статус `Completed` у Fleet rollout означає завершення планування хвиль, а не підтверджене встановлення нової версії на всіх хостах; це інформаційне повідомлення з переходом до результатів. Статуси беруться зі структурованого результату сервера: текст логів не використовується для визначення успіху. `ResultUnknown` вимагає перевірки; отримання задачі агентом саме по собі не є успіхом скрипта.

Права повторно перевіряються перед доставкою push, читанням історії, відкриттям деталей та погодженням. Налаштування сповіщень не надають нових прав. Якщо доступ до модуля чи групи відкликано, відповідні старі сповіщення недоступні. На екрані блокування немає назв хостів, IP, параметрів, логів або секретів.

## Телефон і Web Push

1. Оновіть сервер штатним `update_winhub.sh`: він встановить залежність `pywebpush` та міграцію `20261118_01`. Агенти оновлювати не потрібно.
2. Відкрийте WinHUB за постійною HTTPS-адресою. Сертифікат має бути довіреним браузеру телефона. Agent pin не замінює довіру браузера до сертифіката.
3. На iPhone/iPad з iOS/iPadOS 16.4 або новішою додайте сайт на Home Screen і відкрийте саме цю іконку. На Android скористайтеся `Install app` / `Add to Home screen` у браузері.
4. Увійдіть. На особистому пристрої можна вибрати `Remember this device for 30 days`. Налаштований серверний absolute timeout залишається верхньою межею. Звичайний вхід зберігає поточний idle timeout.
5. Відкрийте дзвіночок → `Notification settings & devices` → `Enable push on this device`. Надайте дозвіл ОС / браузера.
6. Перевірте надходження повідомлення на тестовій задачі або реєстрації тестового хоста. Потім закрийте застосунок та повторіть перевірку.

Web Push потребує вихідного HTTPS-доступу сервера до сервісу браузера. Дозволені push-hosts: `fcm.googleapis.com`, `*.push.apple.com`, `push.services.mozilla.com` / піддомени, `*.notify.windows.com`. Якщо `OUTBOUND_ALLOWED_HOSTS` обмежено, додайте потрібного провайдера до чинного allowlist. TLS-перевірка залишається увімкненою; приватні адреси, нестандартні порти й redirects для доставки push заборонені.

VAPID-пара створюється автоматично при першому ввімкненні push і зберігається зашифрованою у БД. Ручне розповсюдження ключа не потрібне. Це **не** `release-signing-public.pem` агентів. Зберігайте звичайні backup БД і серверного encryption key; не створюйте нову VAPID-пару при кожному update.

Публічна адреса з портом і LAN-адреса є різними browser origins: кожна матиме власну підписку. Рекомендовано використовувати одну постійну адресу. Push може надійти без відкритого WinHUB, але для переходу до деталей телефон повинен мати доступ до сервера, за потреби через VPN.

Доставка push залежить від ОС, браузера, мережі й дозволів; вона не гарантована миттєво. Непрочитана історія зберігається на сервері незалежно від доставки. Повідомлення старше доби не надсилаються через push, але залишаються у шторці. Повторні спроби обмежені п'ятьма; недійсні підписки (HTTP 404/410) вимикаються.

## Налаштування й сеанси

У шторці можна вимкнути спливні картки, обрати категорії push, відмовитися від повідомлень про успіх і задати тихі години в UTC. Це налаштування користувача; дозвіл браузера та підписка належать окремому пристрою. Одночасно дозволено до десяти активних push-пристроїв.

`Push devices → Revoke` вимикає доставку на вибраний браузер. `Remembered sessions → Revoke` завершує довірений сеанс на наступному запиті. Явний `Logout` відкликає поточний remembered session і підписку push. Зміна пароля або 2FA та блокування користувача також припиняють remembered session. Звичайне закінчення idle timeout не видаляє підписку: повідомлення залишається загальним, а деталі потребуватимуть нового входу.

Фонове оновлення дзвіночка не вважається дією користувача і не продовжує idle timeout. Service worker не кешує авторизовані сторінки, API-відповіді або рецепти та не виконує погодження офлайн.

## Погодження з телефона

Картка відкриває адаптивний перегляд актуальних даних. Суперадміністратор може погодити звичайний новий хост, переглянутий шаблон або рецепт Software. Перед підтвердженням сервер перевіряє точну поточну ревізію; за змін даних потрібно оновити сторінку й переглянути їх знову. Підготовка Software та валідація AI-шаблонів залишаються обов'язковими там, де вони потрібні чинним workflow.

Конфлікти ідентичності не погоджуються звичайною кнопкою хоста: `Open workspace` відкриває відповідну вкладку Review з наявними інструментами розв'язання конфлікту. Переходи зі сповіщень до повного workspace не перенаправляються на стартову мобільну сторінку.

## Діагностика та приймання

- Немає дзвіночка: оновіть сторінку без кешу та перевірте, що вхід виконано.
- Історія не поповнюється: перевірте логи `winhub`, роль web і те, що scheduler не вимкнений у web-службі. У службі `winhub-agent` notification workers не запускаються; вона лише записує події разом із результатами агентів.
- Push не працює: перевірте довірений HTTPS, дозвіл ОС, активний запис у `Push devices`, категорію, тихі години та вихідний allowlist. Прострочені/відкликані права також зупиняють доставку.
- Недоступний старий перехід: джерело могло бути видалене або доступ відкликаний; API поверне 404, а не розкриє дані іншого користувача.
- Тест приймання: власна успішна задача, помилкова задача, задача на двох хостах, другий користувач без доступу, погодження іншим суперадміном, відкликання групи, push із закритою іконкою та ручний logout.

Автоматичні перевірки шифрування push і UI не замінюють перевірку на реальному iPhone/Android, із production Nginx, сертифікатом та мережею.
