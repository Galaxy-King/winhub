# Automation Scheduler

[English / Українська](AUTOMATION_SCHEDULER_EN.md)

## Automation Scheduler · як пов'язані його частини


Розклад запускає схвалений Workspace-шаблон на керованих хостах, а не робить backup сервера WinHUB. Сервер обчислює час, створює постійний запис запуску, ставить підписані задачі й отримує автентифіковані результати агентів. Агент забирає задачу під час polling: запланований час не гарантує миттєвий початок скрипта.

## 1. Спочатку підготуй і схвали шаблон


Перевір скрипт backup або обслуговування на одному хості. Він має працювати без інтерактивних запитань, чекати дочірні процеси, перевіряти коди зовнішніх програм і результат операції та явно повертати exit code. Збережи й схвали шаблон у Deployment Builder. Редагування коду скасовує схвалення: Scheduler не запустить його до нового схвалення. Відсутні змінні, відкликані права або недоступні targets блокують запуск.

## 2. Створи розклад


New Schedule → назва, категорія та Launch reason → схвалений шаблон і доступний хост/група → значення змінних. Причина обов'язкова для автоматичного запуску; Run Now запитує причину саме ручного запуску. Склад групи визначається при постановці задачі, тому перевір його перед масовим запуском.

## 3. Обери повторення й перевір наступні дати


Once: одна місцева дата й час. Daily: кожні N календарних днів. Weekly: обрані дні кожні N тижнів від понеділка тижня стартової дати. Backup раз на два тижні: Weekly → every 2 → Sunday → 03:00. Monthly: кожні N місяців конкретного числа, останнього дня або в перший/другий/третій/четвертий/останній день тижня. Відсутня дата, наприклад 31 лютого, пропускається. Fixed interval: фактично минулі хвилини/години/доби від старту; 30 днів не дорівнюють календарному місяцю. Advanced cron: п'ять полів; для точного повторення кожні два тижні використовуй Weekly.

Timezone належить розкладу, не браузеру. Start/End вводяться в ній; зберігання та фільтри історії використовують UTC. Preview показує п'ять наступних дат в обраній зоні. Календарні режими пропускають неіснуючий час при весняному переході та виконують перше повторення один раз при осінньому. Interval рахує фактичний час; Advanced cron використовує правила APScheduler. Перевір Preview біля переходу годинника. End необов'язковий, включно з обраним кінцевим часом.

## 4. Розрізняй доставку та виконання


Delivery window рахується від постановки задачі. Врахуй найбільший інтервал polling, jitter і попередню роботу хоста. Execution time limit починається, коли агент забрав задачу, і передається йому як ліміт роботи. Отримання задачі не доводить, що перша команда backup виконалась. Додатково є дві хвилини на повернення результату. Без фінального результату після цього строку буде Result unknown — не вигаданий успіх або доведений провал backup.

## 5. Накладання, пропущені запуски та повтори


Skip new occurrence: новий запуск позначається Skipped, якщо попередній активний або невизначений. Queue one occurrence: один запуск чекає, наступні накладання пропускаються. Вимкнення розкладу призупиняє очікування; увімкнення дозволяє продовжити. Edit/Disable не зупиняють запущений скрипт. Не видаляй розклад лише для обходу невизначеного запуску — спочатку перевір хост.

Missed run: після відновлення сервера виконується один об'єднаний пропущений запуск або він пропускається. Для Skip допускається затримка до п'яти хвилин. Місячний backlog не відтворюється. Унікальний ключ спрацювання захищає від подвійної постановки різними процесами Scheduler. Перерваний під час постановки запуск стає невизначеним, а не повторюється навмання.

Delivery retries: повторюється лише доставка тієї самої задачі, яку агент ще не прийняв. Є затримка та нове вікно доставки. Прийняті, запущені, невдалі чи невизначені скрипти не перезапускаються автоматично: перший backup може ще працювати, навіть якщо відповідь загублена. Окремо перевіряй ідемпотентність та відновлення власних скриптів.

## 6. Коди результату та перевірка backup


Для нових script-розкладів сервер створює контрольовану обгортку навколо схваленого коду. На хості вона запускає дочірній PowerShell/Bash, фіксує числовий код і додає службовий рядок із унікальним ідентифікатором. Сервер читає лише обмежений формат із автентифікованого результату агента; текст не виконується як код. Це свідчення агента й твого скрипта, не незалежний доказ відновлюваності backup. Якщо рядок відсутній/обрізаний або виконання перервалося — Result unknown. Оновлення агента для обгорток не потрібне, але він повинен підтримувати тип задачі.

Success codes: типово 0. Warning codes: наприклад 10. Verification failure codes: типово 21. Списки не перетинаються. Решта кодів — Script failed. Warning означає завершення з жовтим статусом. Значення кодів задає твій рецепт; backup-утиліта може використовувати іншу систему кодів. Для metric-шаблонів та інших action використовується штатний статус агента, без твердження про числовий контракт обгортки.

PowerShell не завжди кидає виняток через помилку зовнішньої програми: перевіряй `$LASTEXITCODE` або ExitCode процесу з `Start-Process -Wait -PassThru`. Використовуй `$ErrorActionPreference = 'Stop'`, catch та явний exit. У Bash перевіряй статус команди: успішний echo після невдалого backup може приховати помилку. Не відправляй сам backup у фон.

```powershell
$ErrorActionPreference = 'Stop'
try {
    # Запусти власну backup-утиліту та дочекайся завершення.
    # Якщо її код означає помилку: exit 20
    # Виконай її перевірку цілісності архіву.
    # Якщо перевірка не пройшла: exit 21
    # Лише після обох успішних перевірок: exit 0
} catch {
    Write-Output $_.Exception.Message
    exit 20
}
```


Це ілюстрація контракту, не готовий backup-скрипт. Існування файла чи ненульовий розмір не доводять його цілісність. Перевір відновлення на окремій машині. Служба агента працює не від твого desktop-користувача: мережеві диски, облікові дані, права на shares, шляхи й середовище можуть відрізнятися. Секрети передавай через підтримувані секретні змінні, не через назву, причину чи журнал.

## 7. Статуси й історія


Schedules: останній результат, останнє спрацювання, наступний запуск. Run history: окремий запис автоматичного/ручного/заблокованого/пропущеного запуску; результати хостів, exit code, отримання/завершення, спостережувана тривалість, кількість повторів доставки. Фільтри: назва, категорія, джерело, статус, endpoint ID та дати UTC. View log потребує доступу до Queue. Показуються перші 100 дозволених хостів запуску; для великих задач використовуй фільтр endpoint ID та Execution Queue. Старі задачі лишаються в Queue — числові коди та історія спрацювань для них не вигадуються.

Зелений Success: успішний код. Жовтий Warning: погоджений код попередження. Waiting for agent: ще не прийнято. Delivery expired: не доставлено, ця задача не запустила скрипт. Синій Running: прийнято, фінального результату немає. Червоний Script failed: помилковий код. Verification failed: код невдалої перевірки. Dispatch failed: проблема схвалення, прав, змінних чи targets. Partial failure: різні результати хостів із помилкою хоча б одного. Result unknown: немає підтвердження — перевір хост. Cancelled, Missed, Skipped та Resolved manually не є Success.

## 8. Діагностика та сумісність


Немає спрацювання: Enabled, Start/End, timezone, робота Scheduler. Dispatch failed: схвалення, причина, змінні та актуальні права власника. Waiting/Delivery expired: контакти агента, polling, доступ та черга. Script failed: код і журнал на хості. Verification failed: backup і команда перевірки. Unknown: перевір завершення скрипта та всіх дочірніх процесів; лише потім superadmin використовує Resolve manually з причиною для аудиту. Кнопка не зупиняє процеси й не оголошує успіх.

Наявні розклади зберігають старий вираз та штатні результати до редагування. Збереження нової форми вмикає явну політику кодів. Після переходу перевір один хост. Історія підпорядковується retention; невизначені запуски зберігаються, щоб не допустити небезпечного повтору. Для нових UI та обгорток потрібне оновлення сервера, а не обов'язкова нова збірка агента.
