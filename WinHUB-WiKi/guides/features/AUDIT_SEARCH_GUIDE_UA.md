# Аудит, пошук та зберігання історії WinHUB

## Що зберігається

WinHUB зберігає в єдиному пошуку:

- входи, невдалі входи, виходи, завершення сесій та адміністративні дії;
- запуск задачі: виконавець, джерело, шаблон, розклад, хост і групи хоста на момент запуску;
- зашифровані вхідні дані задачі та повний результат агента;
- зведені репорти, початкову згенеровану версію і кожне збережене редагування;
- точний логічний знімок репорту, переданий через email або Confluence, його SHA-256, адресата, виконавця і результат доставки;
- реєстрацію та повторну реєстрацію агентів.

Дані задачі містять snapshot хоста, тому аудит виконання не зникає після видалення або заміни endpoint-а.

## Пошук

Сторінка **Audit, tasks & reports** виконує серверний пошук по всій збереженій давності. Фільтри можна комбінувати: тип події, користувач, роль, джерело, модуль, статус, дія, хост/HWID, Job ID, Template ID і діапазон часу.

Поле пошуку у вмісті підтримує:

- `All words (AND)` — документ має містити кожне введене слово;
- `Any word (OR)` — достатньо одного слова;
- окремий пошук у input/output задачі, current/original, будь-якій revision або точному delivery snapshot репорту.

Вміст задач і репортів залишається зашифрованим у БД. Для пошуку використовуються keyed HMAC blind-index токени; відкритий текст у пошуковій таблиці не зберігається. Пошук у чутливому вмісті доступний лише суперадміну або користувачу з `view_sensitive_reports` у межах його груп хостів.

Після оновлення старі записи індексуються обмеженими пакетами у фоні. Суперадмін може прискорити процес кнопкою **Index older records**.

## Репорти та редагування

Перше створення репорту формує незмінну revision 1. Кожне натискання **Save Changes** створює наступну revision із користувачем, часом, причиною та SHA-256. Збереження використовує optimistic concurrency: застаріла вкладка не може непомітно перезаписати новішу версію.

Перед email/Confluence створюється delivery snapshot. Подальше редагування current revision не змінює ані оригінал, ані вже відправлену копію. Для старих репортів, створених до міграції, revision 1 позначається як `recovered` (migration baseline), бо вже перезаписаний історичний оригінал технічно неможливо відновити.

## Retention

Основні параметри `/etc/winhub/winhub.env`:

```dotenv
HISTORY_RETENTION_DAYS=1825
TELEMETRY_RETENTION_DAYS=30
HISTORY_CLEANUP_BATCH_SIZE=5000
HISTORY_SEARCH_BACKFILL_BATCH_SIZE=250
HISTORY_SEARCH_KEY=replace-with-a-long-random-stable-secret
AUDIT_SENSITIVE_READS=true
```

`HISTORY_RETENTION_DAYS=1825` — п'ять років за замовчуванням. Значення `0` вимикає автоматичне видалення історії. Телеметрія має окремий, коротший термін. Прострочені записи видаляються dependency-safe пакетами; великий backlog продовжує очищатися наступними проходами.

`HISTORY_SEARCH_KEY` потрібно зберігати стабільним і окремо від ключа шифрування. Після його ротації суперадмін має викликати `POST /api/history/reindex` з JSON `{"reset": true, "limit": 2000}`; наступні фонові проходи завершать повну перебудову.

## Видалення і доступ

Hard delete історії задач, репортів, їх версій/доставок, шаблонів і запланованих задач дозволений лише інтерактивній сесії суперадміна. API key та делеговані legacy-права видалення цього не дозволяють. Оператори можуть переглядати лише записи в межах дозволених груп; глобальний аудит входів і дій доступний суперадміну.

Кожен перегляд чутливої деталі, пошук історії, редагування, відправлення, cleanup та hard delete створює окрему подію аудиту.
