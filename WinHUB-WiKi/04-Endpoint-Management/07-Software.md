# Software: каталог ПЗ і кероване встановлення

Software керує Windows-програмами, їхніми наборами та послідовним розгортанням. Файли зберігаються в OMV Files Manager, але агенти завантажують підготовлені копії **лише через WinHUB**. Доступ агента до OMV не потрібний.

## Перше налаштування

Superadmin відкриває **Software → Storage and limits**:

- HTTPS-адреса OMV з портом, без шляху, наприклад `https://omv.internal:3670`;
- за потреби — абсолютний шлях до PEM CA bundle на сервері, наприклад `/etc/ssl/certs/company-ca.pem`;
- глобальні ліміти: типово 2 хости, 2 завантаження, 10 MiB/с, пакет до 4096 MiB.

Сервер повинен мати мережевий доступ до OMV. Для завантажень OMV обов’язкові чинний TLS та `OUTBOUND_POLICY_MODE=enforce`; hostname/IP OMV потрібно додати до наявного `OUTBOUND_ALLOWED_HOSTS`, зберігши решту дозволених інтеграцій. Невідомі redirect-хости не приймаються: потрібне пряме посилання, яке повертає HTTP 200, а не сторінку входу. Cookie браузера Files Manager не використовуються.

`AGENT_PUBLIC_BASE_URL` застосовувався старим транспортом Software; нові Windows-агенти 2.0.1-rc.1 використовують власний ServerUrl, як описано нижче. Для старих задач він використовувався так само, як для пакетів агентів. Він має бути HTTPS і доступним кінцевим хостам. За відсутності використовується HTTPS-адреса, з якої оператор відкрив WinHUB. Для окремого публічного agent-порту задайте цей наявний параметр явно. Nginx main listener та agent-only listener проксіюють `/api/public/software-delivery/` до agent backend без buffering/cache.

Старий PowerShell downloader перевіряє сертифікат WinHUB через системне сховище довіри Windows; новий транспорт 2.0.1-rc.1 описаний нижче. Для власного CA додайте його на кінцеві хости. Agent strict pin сам по собі не додає цей CA у Windows trust store. Вимкнення TLS verification не використовується.

## Додавання програми

1. **Add application**: назва, версія, набори через кому, порядок у наборі.
2. Вставте внутрішнє посилання на файл OMV. Альтернатива — upload файла в розширених параметрах або програма лише зі скриптом, без інсталятора.
3. Для MSI команда тихого встановлення заповнюється автоматично, якщо її залишити порожньою. Для EXE/ZIP/нестандартного пакета задайте власний PowerShell.
4. За потреби задайте окремі рецепти оновлення, видалення та перевірки стану. Дії без рецепта запускати не можна. У розширених параметрах можна замість inline-рецепта вибрати зі списку погоджений шаблон Workspace типу `action/run_script` без змінних/Jinja/AI provenance.
5. Superadmin перевіряє джерело й код і ставить позначку погодження. Зміна виконуваного рецепта, параметрів перевірки або файла скидає попереднє погодження. Редагування лише наборів/порядку не змінює код.
6. Збережіть. Підготовка OMV виконується у фоні, по одному файлу: **Preparation queued** → **Downloading from OMV** → розмір копії у WinHUB. При помилці перевірте сховище/CA/allowlist, відкрийте програму та оберіть повторне завантаження.

WinHUB обчислює SHA-256; якщо введено очікуваний hash із довіреного джерела, він обов’язково має збігтися. Автоматично обчислений hash фіксує отримані байти, але сам по собі не підтверджує їхнього видавця. Копії записуються в `DATA_DIR/software_blobs/<sha256>`; агенту не передаються URL чи ключ публічного посилання OMV. У межах погодженої підготовки сервер прив’язує погодження до отриманого hash; паралельне редагування скидає його за зміни виконуваного вмісту.

Для нової версії змініть версію/посилання й підготуйте пакет. За тієї самої адреси використовуйте **Download the OMV file again**. Для довільної зміни версії запису з локальним upload додайте відповідний новий файл.

## Рецепти

- `{file}` — локальний шлях перевіреного інсталятора;
- `{extract_dir}` — каталог розпакованого ZIP;
- `{package_dir}` — робочий каталог;
- `$PackageName`, `$PackageVersion` — значення з картки як дані, без підстановки в джерельний код.

Рецепт запускається дочірнім PowerShell із очікуванням завершення. Для інсталятора використовуйте `Start-Process -Wait -PassThru` і поверніть його `ExitCode` через `exit`. Типові успішні коди: `0,3010`. Код 3010 показує потребу перезавантаження й зупиняє наступні програми цього хоста; автоматичного reboot немає.

Для перевірки версії рекомендується `command`: `exit 0` означає, що саме потрібний стан уже досягнутий; інший код — що потрібен install/update. Проста наявність файла не відрізняє стару версію від нової. Операція **Install** пропускає вже досягнутий стан; **Update** запускає окремий рецепт і перевіряє результат. **Detect status** нічого не встановлює та не завантажує інсталятор. Для uninstall перевірка має бути false після успішного видалення.

Виконання — від імені служби Windows-агента. Це не встановлення в інтерактивній сесії вибраного користувача. Програми з обов’язковим UI/per-user контекстом потребують окремого перевіреного рецепта; колишній неоднозначний вибір логінів вилучено з цього інтерфейсу.

## Набори та цілі

Одна програма може входити до «Архіватори» і «Стандарт» одночасно. Набір — впорядкований список посилань на програми, а не копії інсталяторів. Менше значення порядку виконується раніше; за однакового порядку — за назвою.

Інтерфейс Software англомовний і використовує спільну темну тему WinHUB. У вкладці **Install**:

1. Виберіть кілька програм та/або наборів.
2. Натисніть **Select endpoints** або **Select groups**. У діалоговому вікні доступні пошук, **Select visible**, список вибраних та **Clear**. Підтвердьте через **Use selected**. **Cancel**, закриття вікна або Escape відкидають непідтверджені зміни; попередній вибір зберігається. Можна поєднати окремі endpoints і кілька groups. На головному екрані показується лише компактний підсумок, а повні списки прокручуються всередині вікна.
3. Перевірте кількість унікальних хостів, порядок програм і дію; перед підтвердженням показується список назв хостів.
4. Вкажіть паралельність у межах глобального ліміту та причину запуску.

Повтори прибираються. Linux/macOS, заблоковані, непогоджені чи недоступні за правами хости спричиняють відмову цілого запуску: змініть вибір, а не покладайтеся на приховані пропуски. Склад цілей, байти пакетів і код фіксуються на момент запуску; наступні зміни каталогу/груп не змінюють уже створене розгортання.

## Навантаження та розгортання

- На кожному хості виконується одна операція Software; наступна програма очікує успіху попередньої.
- Глобальний ліміт активних хостів спільний для всіх розгортань. Додатковий ліміт конкретного запуску може бути нижчим.
- Черга не починає Software на хості з іншою Pending/PickedUp/Running задачею. Це не загальна заборона на сторонні адміністративні задачі, запущені пізніше поза Software.
- Глобальний ліміт завантажень забезпечують DB leases. Кожному потоку відводиться `загальна швидкість / max_downloads`, тому при меншій кількості потоків канал може використовуватися не повністю. Нові значення застосовуються до наступних потоків; уже відкриті завершуються зі старим лімітом.
- Відсутній понад 2 хвилини хост очікує без активного слота. Pending-задача, не забрана за 2 хвилини, повертається в чергу без створення дубліката. Очікування — до 24 годин.
- Помилка або 3010 зупиняє решту програм цього хоста; інші хости продовжують. Після reboot перевірте стан і створіть новий запуск потрібних програм.
- Таймаут агента передається в задачу. За відсутності результату активний слот не звільняється припущенням, що інсталятор уже завершився. Після таймауту + 5 хвилин superadmin може перевірити процеси на хості й натиснути **Resolve manually**, підтвердивши припинення виконання та причину. Це не команда зупинки процесів.
- У **Deployments** доступні прогрес, статус кожної програми/хоста, пауза, продовження та скасування наступних операцій. Поточний інсталятор не переривається. Журнали фактичних задач — у Queue. Повторюйте потрібні програми/хости через каталог; звичайний Retry/Cancel/Finalize для Software job заблоковано.

Для першого запуску використовуйте один тестовий хост, потім малу групу. Погодження коду не доводить нешкідливості інсталятора.

## Оновлення та зберігання

Міграція `20261022_01` додає `software_control`, `software_catalog`, `software_deployments`, `software_steps`. Старий JSON-каталог імпортується при першому відкритті Software, локальні файли копіюються за hash. Оригінали зберігаються; legacy-рецепти не погоджуються автоматично. Старі зовнішні URL треба підготувати через сервер. Старі постійні анонімні download endpoints повертають HTTP 410; старі незавершені задачі з такими URL слід переглянути до оновлення.

Каталог, source URLs і snapshots зберігаються в зашифрованих DB-полях. Тимчасові bearer capabilities доступні лише у payload підписаної задачі; сервер зберігає hash і приймає capability тільки для відповідного активного кроку, поки задачу вже забрав агент і її строк не минув. Це доступ за володінням токеном, а не додаткова криптографічна ідентифікація пристрою під час GET. Закінчена задача, блокування хоста або неправильний токен закривають доступ.

Обов’язкові резервні копії БД, ключів шифрування та `DATA_DIR/software_blobs`. Видалення картки не видаляє незмінні blobs: вони можуть бути потрібні поточним/історичним розгортанням. Автоматичне очищення старих blobs і облік загальної квоти диска в цю версію не входять; контролюйте вільне місце. Одночасно працює одна підготовка OMV; до 1000 хостів, 100 програм і 10000 операцій на запуск; загалом до 50 активних розгортань та 20000 незавершених операцій. Деталі прогресу показуються сторінками по 100 операцій. Основний scheduler WinHUB має бути ввімкнений.

## Регресійна перевірка інтерфейсу

`tests/test_software_ui.py` перевіряє в браузері реальні Software templates разом із CSS з `base.html`: підтвердження/скасування вибору, Escape, перетин груп, пошук, вибір видимих, payload запуску, англійські написи, контраст і мобільні розміри діалогу. Використовуються лише локальні fixture APIs; задачі агентам не надсилаються.

Тест потребує Node.js, Playwright і встановленого браузера. Задайте `WINHUB_PLAYWRIGHT_MODULE` як абсолютний шлях до модуля Playwright; за потреби `WINHUB_PLAYWRIGHT_CHANNEL=msedge`. Із `WinHUB/` запустіть `python -m unittest discover -s tests -p test_software_ui.py -v`. Без явно налаштованого Playwright цей optional test пропускається. Screenshot artifacts можна зберегти поза репозиторієм через `WINHUB_SOFTWARE_UI_ARTIFACT_DIR`.

## Перевірка посилання та сертифікат сховища

У картці програми після вставлення URL натисніть **Test download link**. Перевірка виконується сервером WinHUB із уже збереженими **Storage and limits**, потребує інтерактивної сесії та `manage_software`. POST `/api/infrastructure/software/test-link` приймає JSON `url`; нічого не зберігає й не погоджує. Перевіряються outbound policy, HTTPS origin, TLS, HTTP 200, тип/заявлений розмір відповіді та перші до 1024 байтів. Успіх не гарантує повного завантаження чи правильного SHA-256. Redirect та HTML відхиляються; посилання з токенами не включаються в повідомлення мережевих помилок.

Якщо сертифікат виданий публічно довіреним CA, поле **Server CA bundle** зазвичай залишають порожнім. Для приватного CA отримайте публічні root/intermediate сертифікати у PEM від адміністратора або з TLS-конфігурації сервісу Files Manager на порту 3670 (чи reverse proxy перед ним). Сертифікат адмінпанелі OMV може бути іншим. Приватний ключ копіювати не потрібно. Для самопідписаного сертифіката потрібен його публічний PEM, перевірений за fingerprint через довірений канал; краще використовувати внутрішній CA.

Покладіть bundle на сервер WinHUB, наприклад `/etc/winhub/omv-ca.pem`, надайте користувачу служби право читання та вкажіть абсолютний шлях у **Storage and limits**, збережіть і повторіть тест. Hostname або IP у URL має входити в Subject Alternative Name сертифіката. Додавання CA не виправляє невідповідність імені або прострочений сертифікат. Не завантажуйте невідомий сертифікат із мережі й не довіряйте йому без перевірки. Цей bundle використовується сервером для OMV; довіра Windows-агентів до HTTPS WinHUB налаштовується окремо.

## Покроковий інтерфейс Software

У **Installers · Add / Test link** задайте назву, версію, тип і посилання OMV. **Test download link** перевіряє доступ із сервера без збереження. **Save installer and download** запускає повну підготовку; дочекайтеся **Ready**. При помилці плитка показує повідомлення, **Test this link** переносить її дані у форму для тесту та повторного додавання. Успішний тест доступу ще не замінює повної підготовки. Підготовка продовжується у фоні, список оновлюється автоматично.

У **Add application** виберіть готовий файл у **Installer**, налаштуйте рецепти та збережіть. Посилання вже не вводиться в картці додатка. Файл фіксується за SHA-256: повторна підготовка бібліотеки не підміняє файл у вже створеній програмі або deployment. **Script only / retain existing installer** зберігає поточний файл старої картки; у новій дозволяє сценарій без файла. Старі картки сумісні; для заміни їхнього файла підготуйте новий installer і виберіть його у Edit.

Після збереження superadmin натискає **Review and approve** на плитці додатка, перевіряє код/відбиток і підтверджує. Detection та Workspace templates треба переглянути в **Edit**. Сервер відхиляє погодження застарілої revision. Користувачі без superadmin не мають кнопки погодження. На картках окремо показуються стан файла, погодження й наступна дія; помилка підготовки не приховується за загальним Approval required.

У **Select endpoints** видно Online/Offline (останній контакт протягом 5 хвилин), IP та ОС. Поле пошуку приймає ім'я або IP; знайдений зареєстрований хост додається чекбоксом і **Use selected**. Довільна IP-адреса без агента не створює endpoint і не дозволяє виконання. Права на хости/групи та дедуплікація збережені.

Нові кнопки з'являться на сервері лише після commit/push цих змін та оновлення встановленої програми; локальна зміна checkout не оновлює `/opt/winhub`.

## Доставка Software у Windows agent 2.0.1-rc.1

Нові задачі передають `__software_package`: відносний `/api/public/software-delivery/<step UUID>`, SHA-256, розмір і тимчасовий bearer capability. Агент завантажує через власний **ServerUrl**, тим самим pin-перевіреним HTTPS-клієнтом, що й poll. Глобальний `AGENT_PUBLIC_BASE_URL` більше не вибирає адресу MSI для нових задач; він може залишатися потрібним іншим механізмам. Redirect, інший origin/path, неправильний розмір/hash відхиляються. Агент без capability `software-delivery-v1` отримує вимогу оновлення замість несумісної задачі. Queue показує причину очікування. Сертифікат CA OMV використовується лише сервером, окрема довіра Windows для цього нового downloader не потрібна: чинний pin має збігатися.

У Edit → Action scripts → **Update installer** виберіть **Script only — do not download installer**, якщо програма має власний updater. Це налаштування входить до revision погодження. Install продовжує використовувати вибраний MSI. Сценарії Linux/macOS Software не додаються цим релізом.

Статуси кроку відображають фактичний AgentTask: **Waiting for agent / Received by agent / Running**, а не виділений сервером слот. Старе повідомлення завантаження не відображається після успішного вибору готового installer.

Перехід: оновіть сервер, потім Windows-агент. Старі вже створені задачі можуть містити старий URL у snapshot; завершіть/скасуйте їх через Deployments та створіть новий запуск після оновлення. Новий агент не переписує довільний код старих задач. Для тесту використайте один хост, паралельність 1, перевірте вже встановлену програму через Detection, потім чистий тест install/uninstall на підготовленому хості. Налаштування доступу до OMV залишається на сервері.
